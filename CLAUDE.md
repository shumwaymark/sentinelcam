# SentinelCam Development Guide

**Repository**: https://github.com/shumwaymark/sentinelcam

Distributed computer vision and machine learning pipeline on embedded Raspberry Pi hardware. Stand-alone system — no cloud services or external infrastructure for core components. Hub-and-spoke architecture with camera nodes reporting to data sinks and analysis engines. Designed for incremental, evolving recognition model development and deployment. Persons and vehicles are the first two use cases.

See `HISTORY.md` for the full version changelog. See `README.rst` for the project narrative.

## Design Constraints

1. **Power Budget**: Raspberry Pi nodes run on low voltage (<5W typical)
2. **Memory Limits**: 500MB–1GB RAM per process on Pi 4/5
3. **Network Architecture**: Hub-and-spoke data acquistion, logfile publishing 
4. **Frame Rate Target**: 30 FPS for live viewing and smooth playback
5. **Storage**: Filesystem storage on central datasinks provisioned with USB3 or NVMe SSD
6. **Deployment**: All provisioning, configuration, and code/model distribution is Ansible-managed. Do not add or change service deployments outside the Ansible framework

## Architecture — Who Talks to Whom

```
Outpost ──PUB/SUB (ImageZMQ :5567)──→ CamWatcher (ImageStreamWriter child processes)
Outpost ──PUB/SUB (ZMQ :5565)──────→ CamWatcher (async log subscriber)
CamWatcher ──REQ/REP (ZMQ :5566)──→ Sentinel (task submissions)
Sentinel ──PUB (ZMQ :5565)─────────→ CamWatcher (SentinelAgent subscribes to results)
Sentinel ──PUB (ZMQ :5565)─────────→ Watchtower (subscribes to results + alerts)
Sentinel ←─REQ/REP (ImageZMQ :5556)─ DataPump (TaskEngine DataFeed requests)
Watchtower ←REQ/REP (ImageZMQ :5556) DataPump (event replay data)
Watchtower ──SUB (ImageZMQ :5567)──→ Outpost (live viewing)
```

Within a process: ZMQ `ipc://` sockets for parent↔child signaling (RingWire, LensWire). Never `tcp://127.0.0.1` for same-machine IPC.

Port assignments are centralized in `devops/ansible/inventory/group_vars/all/sentinelcam_ports.yaml`.

## Core Technologies — Do Not Substitute

- **Transport**: ImageZMQ for images, ZeroMQ for logs/control/events
- **Multiprocessing**: Python `multiprocessing` (NOT threading) for parallel image work. GIL avoidance is the reason
- **Shared Memory**: `RingBuffer` (sharedctypes.RawArray wrapped as NumPy arrays) for zero-copy image exchange
- **IPC Signaling**: `RingWire` / `LensWire` (ZMQ REP/REQ over `ipc://`) with non-blocking poll
- **Serialization**: MessagePack for structured IPC data, pickle for DataFrames over DataFeed
- **JPEG Encoding**: `simplejpeg` library (not OpenCV imencode)
- **Async**: `zmq.asyncio.Context` for event loops; `zmq.Context.shadow(asyncCtx.underlying)` for blocking ops alongside async
- **Data Analysis**: pandas DataFrames throughout

## Key Design Patterns

### Multiprocessing + Shared Memory (Sentinel)
- `RingBuffer` allocates `sharedctypes.RawArray` blocks, wraps them as NumPy arrays
- Parent process (`JobManager` thread) writes decoded frames into the buffer with `put()`
- Child process (`JobTasking`) reads by shared memory index from `get()` — no data copying
- `frame_complete()` **must** be called before the next `get()` to avoid race conditions
- Ring buffer dimensions must be known at startup — configured in `sentinel.yaml` `ring_buffer_models`

### Multiprocessing + Shared Memory (SpyGlass)
- `LensTasking` uses a single `sharedctypes.RawArray` frame buffer (not a ring)
- Parent writes current frame, sends lens request over IPC
- Child processes frame, sends results back
- One frame at a time — poll for results before sending next. Never blocks the main pipeline

### Async Event Loop (CamWatcher, Sentinel)
- `asyncio.gather()` runs multiple coroutines: control loop, log processing, alert sending
- ZMQ sockets created from `zmq.asyncio.Context`
- Blocking ZMQ operations use `zmq.Context.shadow()` of the async context

### Process Initialization Sequence
1. Parent creates shared memory buffers
2. Parent creates IPC socket (REP/Hub side)
3. Parent forks child process
4. Child creates IPC socket (REQ side), connects
5. Child sends handshake
6. Parent receives handshake, connects result publisher
7. Parent replies — child may proceed

This is followed by both Sentinel TaskEngines and SpyGlass LensTasking. The order matters.

### Job Lifecycle (Sentinel)
Submit → Queued → On-deck → Running → Done/Failed/Chained. Tasks support priority (1=real-time post-event, 2=default, 3=background). Task chaining and aliasing configured in YAML. The `JobManager` thread continuously: services ring buffers for running tasks, assigns queued jobs to idle engines by class affinity, and ventilates the queue.

### Log-Based Event Protocol
Outpost logs carry `ote` (object tracking event) prefixed JSON messages. Message types: `start` (new event), `trk` (tracking record), `end` (event complete with sentinel task list). CamWatcher parses these to drive image capture, CSV writing, and sentinel task submission.

## Data Model

### Filesystem Structure (on data sinks)
```
~/sentinelcam/camwatcher/YYYY-MM-DD/camwatcher.csv           # Event index (no header)
~/sentinelcam/camwatcher/YYYY-MM-DD/{EventID}_{type}.csv     # Tracking detail (with header)
~/sentinelcam/images/YYYY-MM-DD/{EventID}_{Timestamp}.jpg    # Captured frames
```

**Event index columns**: node, viewname, timestamp, event (UUID), width, height, type

**Tracking detail columns**: timestamp, objid, classname, rect_x1, rect_y1, rect_x2, rect_y2

Event data is always scoped by date. No cross-date indexing. All identifiers are UUIDs. Multiple tracking types per event are supported (e.g., `trk` from Outpost, `fd1` from Sentinel face detection).

### Key Principles
- **`group_vars/all/sentinelcam_standards.yaml`** defines paths, users, directory layout, code deployment mappings, venv paths, network buffer sizes, and logging standards. All roles reference these — never hardcode paths
- **`group_vars/all/site.yaml`** contains the **outpost registry**: the single source of truth mapping outpost nodes → hostnames → cameras → datasinks. CamWatcher and Watchtower YAML configs are auto-generated from this
- **`group_vars/all/model_registry.yaml`** tracks model versions with YYYY-MM-DD timestamps. Rollback is a config edit + playbook run. Models persist on disk; only the config/service restart switches versions
- **Code deployment** is rsync-based from primary datasink. The `code_deployment.components` structure in `sentinelcam_standards.yaml` maps each component to source/destination paths. Adding a new service means adding an entry — no changes needed to the base role
- **Configuration files** are Jinja2 templates in each role's `templates/` directory, rendered from inventory variables. The YAML files in the repo root are reference examples only — deployed configs come from Ansible
- **Service management** uses systemd. Each role has handlers for service restart on code/config changes

### When Modifying Ansible
- New outpost node? Add to `site.yaml` outpost registry + `production.yaml` inventory + `host_vars/` if needed
- New model? Add to `model_registry.yaml`, create registry folder on datasink, run `deploy-models.yaml`
- New component? Add to `code_deployment.components` in `sentinelcam_standards.yaml`, create role, create playbook
- Configuration change? Edit the appropriate `group_vars` or `host_vars`, run the deploy playbook. Do not edit deployed configs directly on nodes
- The Ansible encrypted vault (`vault.yaml.template`) holds example SSH keys and secrets. For use with `ansible-vault` when deployed

## CI/CD Pipeline — Code Transmission and Deployment

See `devops/README.rst` for the full narrative. The pipeline moves code from development workstation to production nodes through a 4-stage chain. Each stage has a single responsibility and the pipeline is fully automated end-to-end after the developer initiates `deploy.py`.

### Pipeline Flow
```
Workstation ──SCP──→ Bastion ──rsync──→ Data Sink (data1) ──SSH──→ Ramrod (buzz)
  deploy.py      process-code-     integrate-code-         sync-ramrod-from-
                  upload.sh         update.sh               datasink.sh
                                                                 │
                                                          Ansible playbooks
                                                                 ↓
                                                          Target Nodes
```

### Stages

1. **Workstation** (`deploy.py`): Creates a timestamped ZIP of selected components (imagenode, sentinel, watchtower, etc.), transfers via SCP to bastion, triggers downstream processing. Supports `--dry-run` and multi-component packages
2. **Bastion** (`process-code-upload.sh`): Airlock — validates and forwards packages to data1 but **never executes code**. Security boundary between external development and internal production network
3. **Data Sink** (`integrate-code-update.sh`): Backs up current state, integrates new code into `current_deployment/`, creates `.deploy_flags/{component}` markers indicating what changed, notifies ramrod
4. **Ramrod** (`sync-ramrod-from-datasink.sh`): Pulls fresh devops toolchain from data1, reads deployment flags, runs Ansible playbooks only for changed components against the appropriate host groups

### Key Scripts
| Script | Runs on | Location |
|--------|---------|----------|
| `deploy.py` | Workstation | `devops/scripts/sync/deploy.py` |
| `deployment-config.yaml` | Workstation | `devops/scripts/sync/deployment-config.yaml` |
| `process-code-upload.sh` | Bastion (rocky@chandler-gate) | `devops/scripts/sync/process-code-upload.sh` |
| `integrate-code-update.sh` | Data sink (ops@data1) | `devops/scripts/sync/integrate-code-update.sh` |
| `sync-ramrod-from-datasink.sh` | Ramrod (ops@buzz) | `devops/scripts/sync/sync-ramrod-from-datasink.sh` |

### Design Principles
- **Deployment is testing**: Real hardware on an isolated network is the only meaningful test environment. The pipeline provides rollback safety rather than pre-deployment test gates
- **Airlock pattern**: The bastion cannot execute code — it only validates and transfers. A compromised bastion cannot compromise the production network
- **Selective deployment**: Deployment flags ensure only changed components get redeployed. No accidental full-stack redeployment
- **Automatic rollback checkpoints**: `integrate-code-update.sh` creates timestamped backups of `current_deployment/` and `devops/ansible/` before every integration
- **Self-updating pipeline**: Integration scripts copy themselves to `~/scripts/` so future runs use the latest version
- **Permission normalization**: Windows filesystem artifacts (carriage returns, permissions) are automatically fixed during data1 integration

### Ramrod Health Monitor (`ramrod/ramrod_health.py`)
Separate from the deployment pipeline, the ramrod node runs a health observer via cron every 3 minutes:
- Queries CamWatcher, DataPump, and Sentinel via ZMQ REQ/REP
- Derives per-outpost health from heartbeat data
- Detects stale outposts (>600s without heartbeat triggers alarm)
- Submits SYSHEALTH reports to Sentinel for broadcast to all subscribers (including Watchtower)

## Network Topology

All nodes are on a private `192.168.10.0/24` network. A bastion host (`chandler-gate`) provides external access via WireGuard tunnel to a VPS on `10.0.0.0/24`. Video exports are `scp`'d to the VPS and shared via Nginx secured links with time-expiring MD5 hashes, delivered through a Telegram bot.

Current production nodes: 3 outposts (east, lab1/outpost, alpha5), 1 datasink (data1), 1 sentinel, 1 watchtower (wall1), 1 ML trainer (deepend/Jetson Nano).

## Component Responsibilities

### Outpost (`outpost.py` → imagenode Detector)
- Motion detection via MOG2 background subtraction within ROI — runs every frame in main pipeline
- Publishes JPEG frames at 30 FPS via ImageZMQ PUB (:5567)
- Publishes event logs via ZMQ PUB (:5565) — `ote`-prefixed JSON for tracking, `fps`-prefixed for heartbeat
- SpyGlass child process for object detection/tracking (MobileNetSSD, YOLOv3, dlib/OpenCV trackers)
- DepthAI OAK cameras provide on-camera MobileNetSSD at 30 FPS + hardware JPEG encoding
- `interesting_objects` config controls which detections trigger events and sentinel tasks
- `sentinel_tasks` config maps object classes to sentinel task names submitted post-event
- Heartbeat every 5 minutes: `fps(tick_count, looks, events, tick_rate, measured_fps)`

### CamWatcher (`camwatcher.py`)
- Main async event loop: `asyncio.gather(control_loop, process_logs, alert_sender)`
- `ImageStreamWriter` child process per outpost — subscribes to image publisher, writes JPEG files
- `CSVwriter` I/O thread — writes tracking detail CSV from queue
- `CSVindex` child process — single point of control for event index mutations (prevents corruption)
- `SentinelAgent` child process — subscribes to sentinel log publisher, captures task results to CSV
- Post-event: automatically submits sentinel tasks based on outpost `sentinel_tasks` config
- Control port (:5566) accepts: `CamUp` (dynamic outpost registration), `Agent` (ad hoc sentinel agents), `DelEvt` (event deletion, internal use only)
- Alert forwarding: event deletions sent to sentinel for re-broadcast to all subscribers

### DataPump (`datapump.py`)
- REQ/REP server on :5556, subclass of `imagezmq.ImageHub`
- Serves: `get_date_index()`, `get_tracking_data()`, `get_image_list()`, `get_image_jpg()`
- Returns pandas DataFrames (pickled), timestamp lists, JPEG buffers
- FaceList integration for face data management
- To be extended: storage analysis, cleanup reporting, capacity monitoring

### DataFeed (`datafeed.py`)
- Client library, subclass of `imagezmq.ImageSender`. Used by Sentinel TaskEngines and Watchtower
- Raises `TrackingSetEmpty`, `ImageSetEmpty` exceptions for missing data
- Built-in timeout handling with socket close/reconnect on DataPump failures

### Sentinel (`sentinel.py`)
- Async main loop: `asyncio.gather(task_loop, task_feedback)`
- `task_loop`: REP socket receiving JSON job requests and control commands (HISTORY, STATUS, ALERT)
- `task_feedback`: SUB socket collecting results from TaskEngine IPC publishers
- `JobManager` thread: services ring buffers, assigns jobs by class/priority, handles chaining
- `TaskEngine` instances: each owns a forked `JobTasking` child process, RingBuffer set, RingWire, task queue
- Ring buffers sized per `ring_buffer_models` config — dimensions must match expected camera resolutions
- Task engines have class affinity and accelerator assignment (cpu, ncs2, coral)
- Alert re-broadcast: system-wide alerts forwarded to all log subscribers
- Logging is exclusively via ZMQ PUB — sentinel does not write local log files

### Watchtower (`watchtower.py`)
- Tkinter kiosk app designed for Pi 7" touchscreen (800×480)
- Player subsystem: `PlayerDaemon` child process for image decoding, ring buffer, frame display
- Subscribes to sentinel log publishing — auto-updates display on new events with inference overlays
- Event history browser by outpost view and hourly time slot
- System health and status display, monitoring, and reporting
- Video export: stitches multi-segment events into MP4 with bounding box overlays, uploads to VPS via SCP
- Motion calibration tool: live parameter tuning with real-time visual feedback
- State machine: STARTING → LOADING → READY → PLAYING → PAUSED → IDLE, with DaemonState coordination

## ML Pipeline — Facial Recognition

- **Face detection**: OpenCV DNN (ResNet-10 SSD), Google Coral EdgeTPU model, or BlazeFace (MediaPipe)
- **Embeddings**: OpenFace DNN (128-dimension unit hypersphere via Torch model)
- **Classification**: SVM classifier (scikit-learn) trained on collected embeddings
- **Ensemble**: Model probability threshold + Euclidean distance fallback against per-person baselines
- **Open-set**: Distance metric distinguishes "low confidence on known" vs "genuinely unknown"
- **Learning cycle**: Casual data collection → face detection → embedding → candidate selection (`FaceSweep`) → data update (`FaceDataUpdate`) → retrain → deploy via model registry
- **Data files**: `facemodel.pickle` (SVM), `baselines.hdf5` (per-person reference embeddings), `facelist.csv` (face inventory), `facedata.hdf5` (all embeddings)
- **Task chain**: `MobileNetSSD_allFrames` → `GetFaces` → `FaceRecon` (configured via YAML chaining)

## Anti-Patterns — Avoid These

1. **Threading for image processing** — GIL kills performance. Use multiprocessing
2. **Blocking the main Outpost pipeline** — Defer heavy work to SpyGlass/Sentinel
3. **Uncompressed image transport** — Always JPEG via simplejpeg
4. **Storing data on Outpost nodes** — No disk. All persistence at data sinks
5. **System clock for timestamps** — Use image-capture metadata timestamps
6. **Python queues for image data** — Use RingBuffer shared memory
7. **`tcp://127.0.0.1` for same-machine IPC** — Use `ipc://` (proven latency improvement, see v0.0.5)
8. **Calling `frame_complete()` before child is done** — Race condition
9. **Mixing blocking/async ZMQ carelessly** — Use `Context.shadow()` for blocking ops alongside async
10. **Editing deployed configs directly on nodes** — Use Ansible. Deployed configs are template-generated
11. **Hardcoding paths, ports, or hostnames** — Reference `sentinelcam_standards.yaml` and `sentinelcam_ports.yaml`

## Safe vs. Risky Modifications

### Safe — extend freely:
- New `TaskFactory` task classes (add to `taskfactory.py`, create YAML config in `tasks/`)
- New SpyGlass lenses (add to `lenses.py`)
- Watchtower UI features (new pages, controls)
- Ansible roles and playbooks for new node types or services
- Model registry additions
- Pipeline tuning (motion parameters, skip_factor, detection thresholds)
- Data analysis notebooks in `twister/`

### Risky — requires deep understanding of why current patterns exist:
- RingBuffer/RingWire internals
- Multiprocessing initialization sequences and handshakes
- ImageZMQ transport layer
- Main Outpost pipeline flow (outpost.py `object_tracker`)
- ZMQ socket lifecycle (close semantics, context management)
- Shared memory allocation and cleanup
- Async event loop structure in CamWatcher/Sentinel
- JobManager thread scheduling logic

| Memory per process | 200–800MB on Pi |
| Startup time | 5–15s per component |

## Logging

- ZMQ PUB/SUB aggregates all logging centrally. Sentinel publishes on :5565, outposts on :5565
- Log topics: `{nodename}.{LEVEL}` (e.g., `east.INFO`, `sentinel.ERROR`)
- Special prefixes: `ote` = object tracking event (JSON), `fps` = heartbeat
- CamWatcher collects outpost + sentinel logs. Watchtower subscribes to sentinel logs
- Sentinel does **not** write local log files — everything goes through ZMQ publishing
- **Always check logs first.** They contain the answer
